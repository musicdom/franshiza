# Franshiza — MAX Business Solutions

Премиальная витрина продуктовых концепций для ботов и мини-приложений под бизнес-задачи в MAX. Сейчас это статический фронтенд-каталог; он не утверждает, что перечисленные решения уже разработаны или подключены к MAX.

## Текущий статус

- Каталог содержит 24 концепции для разных отраслей.
- Поиск работает по названию, описанию, категории, аудитории, функциям и тегам.
- Фильтры по отрасли, типу решения и статусу работают на клиенте.
- Карточка открывает подробное описание продукта и его сценария.
- Форма проверяет обязательные поля и согласие, но **не отправляет и не сохраняет данные**: серверный backend не подключён.
- Административная панель и авторизация не реализованы. Не публикуйте в этом статическом проекте заявки или приватные данные.
- Все продукты помечены «Концепция», пока их фактическая готовность не подтверждена.
- Визуальные макеты — иллюстрации интерфейсов, не скриншоты действующих ботов.

## Локальный запуск

Это статический сайт без сборщика и обязательных npm-зависимостей. Откройте `index.html` в браузере либо запустите локальный HTTP-сервер из корня репозитория:

```bash
python3 -m http.server 8080
```

Затем откройте `http://localhost:8080`.

## Проверки качества

Требуется Node.js 20 или новее. Зависимости устанавливать не нужно:

```bash
npm run verify
```

Команда проверяет синтаксис `app.js` и целостность каталога: минимальное число концепций, уникальность ID, обязательные поля, отраслевое покрытие и корректный статус «Концепция». GitHub Actions запускает проверки при push в рабочую ветку и при открытии pull request в `main`. Это не заменяет ручное тестирование интерфейса в браузере.

## Структура

- `index.html` — главная страница, каталог, FAQ и формы.
- `styles.css` — дизайн-система и адаптивная верстка.
- `app.js` — данные каталога, поиск, фильтры, карточки, форма в демонстрационном режиме.
- `robots.txt` — базовые правила для поисковых роботов.
- `package.json` и `tests/catalog.test.js` — команды и проверки целостности каталога.
- `.github/workflows/quality.yml` — автоматические проверки на GitHub Actions.
- `sitemap.xml` пока не добавлен: сначала нужно определить production-домен, чтобы не публиковать неверные URL.

## Как добавить продукт

В `app.js` добавьте объект в массив `PRODUCTS`. Обязательные поля: `id`, `name`, `category`, `type`, `status`, `icon`, `tone`, `summary`, `problem`, `features`, `audience`, `steps`, `price`, `level`, `tags`. Уникальный `id` используется в URL `?product=...`.

Допустимые статусы: `concept`, `development`, `ready`. Ставьте `ready` только после проверки работающего продукта. Цену задавайте согласованную; иначе оставляйте «Стоимость по запросу».

## Публикация

Сайт можно развернуть на любом статическом хостинге, который отдаёт файлы из корня репозитория. На GitHub Pages включите Pages для ветки/папки, выбранной для публикации. Для собственного домена обновите canonical/OG URL и sitemap после выбора домена.

Проверки перед production:
1. Проверить страницу и мобильную версию в реальном браузере.
2. Проверить доступность шрифтов и поведение при их блокировке.
3. Проверить все фильтры, карточки, диалоги и валидацию формы.
4. Добавить уникальные индексируемые страницы продуктов, canonical URL, актуальный sitemap и корректные OG-изображения.
5. Подключить серверный API и защищённое хранилище заявок, затем изменить форму так, чтобы она показывала успех только после подтверждённого ответа API.
6. Реализовать серверную авторизацию для административной панели, проверку прав на каждом API-маршруте, CSRF-защиту где применимо, ограничение частоты запросов, антиспам и валидацию данных.
7. Настроить политику конфиденциальности, согласие на обработку данных и сроки хранения.
8. Проверить MAX Mini App/бот-интеграцию отдельно; не считать наличие витрины подтверждением интеграции.

## Backend и административная панель — следующий этап

Для настоящего приёма заявок требуется API (например, серверные функции выбранного хостинга), база данных и настройка секретов через менеджер переменных окружения хостинга. Для админки нужна серверная сессия/провайдер авторизации и проверка роли на стороне сервера. Не храните пароль администратора, токены или ключи в `app.js` и не открывайте заявки через публичный API.

Не подключайте платежи до проверки провайдера, безопасной серверной обработки уведомлений и подтверждения статуса платежа на сервере.
