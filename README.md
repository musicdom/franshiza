# Franshiza — MAX Business Solutions

Премиальная витрина концепций ботов, Mini Apps и автоматизации бизнес-процессов под MAX. Рабочая реализация каждого продукта подтверждается отдельно; карточки не заявляют неподтверждённые интеграции.

## Текущий функционал

- Каталог из 24 концепций для разных отраслей, поиск, фильтры и подробные карточки.
- Форма отправки заявки через `POST /api/requests`.
- Серверное хранение заявок в Redis через Upstash REST API, срок хранения записи — до 180 дней.
- Уведомления в MAX через официальный Bot API, если настроены токен и ID чата.
- Закрытая админ-панель `/admin.html`: пароль администратора, подписанная HttpOnly-сессия, просмотр последних заявок и смена статусов.
- Защита от запросов с чужого Origin, ограничение частоты запросов, заголовки безопасности и fail-closed поведение при отсутствии конфигурации.
- Политика обработки данных-шаблон `privacy.html`. Публичный приём заявок остаётся выключенным, пока владелец не заполнит сведения об операторе и явно не подтвердит готовность политики.

## Важное ограничение хостинга

API использует формат Node.js serverless functions, совместимый с Vercel. **Обычный статический хостинг, включая GitHub Pages, не исполняет файлы в `api/`**. В доступных подключённых аккаунтах Vercel на момент разработки проект, связанный с `musicdom/franshiza`, не обнаружен. Поэтому код подготовлен в ветке, но рабочий backend не развёрнут и реальный приём заявок пока не подтверждён. Перед включением нужно связать этот репозиторий с существующим хостингом, который поддерживает эти API routes, или адаптировать маршруты к фактическому хостингу.

## Настройка секретов

Скопируйте имена из `.env.example` в секреты/переменные окружения **хостинга**, не в Git и не в клиентский код:

- `UPSTASH_REDIS_REST_URL` — HTTPS URL вашего Upstash Redis REST API.
- `UPSTASH_REDIS_REST_TOKEN` — токен Upstash Redis REST API.
- `ADMIN_PASSWORD` — уникальный пароль не короче 16 символов.
- `SESSION_SECRET` — случайный секрет не короче 32 символов.
- `MAX_BOT_TOKEN` — токен бота MAX; обязателен только для уведомлений.
- `MAX_ADMIN_CHAT_ID` — ID личного диалога или чата, куда бот вправе отправлять сообщения.
- `DATA_CONTROLLER_NAME` и `DATA_CONTROLLER_CONTACT` — проверенные данные оператора, которые также нужно внести в `privacy.html`.
- `PRIVACY_POLICY_APPROVED` — оставить `false` до завершения правовой проверки и публикации заполненной политики; только затем установить `true`.

Backend намеренно отвечает ошибкой, если обязательные переменные отсутствуют. Секреты не создаются автоматически и не зашиваются в исходники. Для MAX используется `POST https://platform-api2.max.ru/messages?chat_id=...` с токеном в заголовке `Authorization`; бот должен иметь доступ к выбранному чату. См. [официальную документацию MAX](https://dev.max.ru/docs-api/methods/POST/messages).

## Безопасность и эксплуатация

- Админ-сессия подписывается HMAC-SHA256 и хранится в cookie `HttpOnly; Secure; SameSite=Strict` сроком до 8 часов.
- Пароль и секрет сессии никогда не возвращаются клиенту.
- API не пишет контактные данные в логи и возвращает нейтральные сообщения об ошибках.
- Вход ограничен 8 попытками за 15 минут с одного IP-ключа; отправка заявок — 5 попытками за 15 минут.
- Записи хранятся до 180 дней; индекс просроченных записей очищается при новых заявках.
- Уведомление MAX — best effort: если MAX недоступен, заявка остаётся в хранилище. Админ-панель показывает состояние уведомления.
- `robots.txt` не является защитой доступа. Защита админ-API реализована на сервере.
- До публичного запуска владелец должен заполнить и проверить `privacy.html`, установить контакты оператора и проверить применимые требования к обработке и месту хранения персональных данных.

## Локальные проверки

Требуется Node.js 20+. Внешние npm-зависимости не нужны:

```bash
npm run verify
```

Проверка выполняет синтаксический анализ фронтенда, админки и всех API-модулей, а также тесты целостности каталога и подписанных сессий. GitHub Actions выполняет эти проверки автоматически. Это не заменяет тестирование на реальном хостинге, проверку Redis, MAX и мобильных браузеров.

Для просмотра только статической части можно запустить:

```bash
python3 -m http.server 8080
```

При этом API не будет работать на таком сервере.

## Структура

- `index.html`, `styles.css`, `app.js` — витрина и форма заявки.
- `admin.html`, `admin.css`, `admin.js` — закрытая панель управления заявками.
- `api/requests.js` — приём публичных заявок.
- `api/admin/*.js` — вход, выход, список заявок и обновление статуса.
- `lib/server/*.js` — конфигурация, безопасность, Redis-хранилище и уведомления MAX.
- `privacy.html` — шаблон политики обработки данных; требует заполнения и правовой проверки.
- `vercel.json` — заголовки безопасности для Vercel.
- `tests/` и `.github/workflows/quality.yml` — тесты и CI.

## Следующие шаги перед production

1. Подтвердить фактический хостинг и связать с ним репозиторий/ветку.
2. Создать Redis REST database и добавить секреты в панели хостинга.
3. Заполнить реквизиты оператора в политике, проверить текст и только потом включить `PRIVACY_POLICY_APPROVED=true`.
4. Добавить токен MAX и реальный ID чата, проверить, что бот может писать в этот чат.
5. Протестировать создание заявки, уведомление, вход в админку, обновление статуса и поведение при отключённом Redis/MAX.
6. Провести браузерные и мобильные тесты, затем развернуть preview и проверить её вручную.

`main` не менялась. Изменения остаются в ветке `feat/premium-max-business-platform`.
